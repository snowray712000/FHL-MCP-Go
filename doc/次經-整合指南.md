# 次經：信望愛 API 整合指南

給另一個專案做設計、規畫、實作時參考。內容取自本專案（FHL-MCP-Go 1.2.1）的程式與測試，並在 2026-10-19 對上游做了一輪實測（約 20 次 GET），不是從 README 推測。
來源檔案：`internal/fhlapi/client.go`（`QSub` / `SESub`）、`internal/bible/scripture.go`、`internal/bible/scripture_books.json`、
`internal/tools/tools_scripture.go`、`internal/tools/m2g_test.go`、`tests/fixtures/upstream/qsub_*`、`sesub_*`、`tests/fixtures/golden/*apocrypha*`、
`tests/oracle/scripture_oracle.py`、`doc/m0/tool-matrix.md`（D24）。

標示「未驗證」的是本專案沒有實測過的部分，請在新專案自行確認。標示「2026-10-19 實測」的是這次直接連上游得到的結果。

## 1. 一句話摘要

次經（上游版本代碼 `c1933`，「1933年聖公會出版」）由信望愛 Bible API 的兩支 PHP 端點提供：`qsub.php` 查經文，`sesub.php` 搜關鍵字。
書卷清單沒有上游端點，要自己維護一張 15 本的靜態表（編號 101–115）。使徒教父（`qaf.php` / `seaf.php`，編號 201–217）是同一套寫法，本專案用同一個引擎處理兩者；
使徒教父另有 `doc/使徒教父著作-整合指南.md`。

## 2. 上游 API

基底網址：`https://bible.fhl.net/api/`，全部 HTTP GET，回 JSON（`Accept: application/json`）。本專案送 `User-Agent: FHL-MCP-Go`，逾時 30 秒，回應最多讀 8 MiB。官方說明頁：`https://bible.fhl.net/json/`。

### 2.1 `qsub.php`：查經文

| 參數 | 說明 |
| --- | --- |
| `bid` | 書卷編號 101–115（見 §4） |
| `chap` | 章 |
| `strong` | 固定送 `0` |
| `sec` | 節，可省略；省略 = 整章。格式 `1`、`1-5`、`1,3,5`、`1-2,5,8-10` |
| `gb` | 選用。`1` = 回傳簡體（2026-10-19 實測有效，見 §3.4）。**本專案目前沒送這個參數** |

實際請求例：`qsub.php?bid=103&chap=1&strong=0&sec=1-3`

回應（取自 `tests/fixtures/upstream/qsub_tob_1_1-3.json`，中文是 `\uXXXX` 跳脫，這裡已還原）：

```json
{
"status":"success",
"record_count":3,
"v_name":"1933年聖公會出版",
"version":"c1933",
"proc":0,
"record":[{"engs":"Tb","bid":103,"chineses":"比","chap":1,"sec":1,"bible_text":"這書是多比的自述。他是多比爾的兒子、…屬於拿弗他利支派。"},
          {"engs":"Tb","bid":103,"chineses":"比","chap":1,"sec":2,"bible_text":"多比當亞述王撒縵以色在位的時候、…"},
          {"engs":"Tb","bid":103,"chineses":"比","chap":1,"sec":3,"bible_text":"我多比一生一世、按着眞實義氣爲人、…"}],
"prev":{"chineses":"馬二","bid":102,"engs":"2Mc","chap":15,"sec":39},
"next":{"chineses":"比","bid":103,"engs":"Tb","chap":1,"sec":4}
}
```

重點：
- 數字欄位（`bid`、`chap`、`sec`、`record_count`）上游有時是數字、有時是字串。2026-10-19 實測整個 `sesub.php` 的 4723 筆命中全是整數，但本專案仍用 `json.RawMessage` 原樣保留（見 §3.5），因為 Python 版輸出就是原樣傳遞。新專案若用強型別，要有型別不固定的防備。
- `prev` / `next` 是上一節、下一節的位置（跨章、跨書都會給）。`bid=101` 的第一節沒有 `prev`。本專案沒用到，但做「上一章／下一章」導覽時是現成資料。
- `proc` 固定 `0`，`engs` 是上游自己的書卷縮寫（`Tb`、`Jth`、`Ws`、`Re` 等，與本專案縮寫不同），`chineses` 是上游簡稱（`比`、`滴`、`所`…）。
- 章節不存在時仍回 `status:"success"`，`record_count:0`、`record:[]`（fixture `qsub_tob_99.json`）。這不是錯誤。
- 單章書（耶利米書信 110、瑪拿西禱詞 111、三童歌 112、蘇撒拿傳 113、彼勒與大龍 114）章號就是 `1`：實測 `bid=110&chap=1` 回 73 節，`bid=111&chap=1&sec=1-2` 回 2 節。

### 2.2 `sesub.php`：關鍵字搜尋

| 參數 | 說明 |
| --- | --- |
| `q` | 關鍵字（本專案一律先轉成繁體，見 §3） |
| `offset` | 跳過筆數 |
| `limit` | 回傳筆數。**不可超過 500**（見下） |
| `gb` | 選用。`1` = 回傳簡體（2026-10-19 實測有效）。本專案沒送 |

請求例：`sesub.php?limit=3&offset=0&q=%E6%99%BA%E6%85%A7`（參數依字母排序，是 Go `url.Values.Encode()` 的結果）。

回應：`{"status":"success","orig":"0","key":"智慧","record_count":3,"record":[{id,chineses,bid,engs,chap,sec,bible_text}, ...]}`

重點（以下數字為 2026-10-19 實測）：
- 命中以全域 `id`（跨整個次經的流水號）排序，也就是書卷順序、章、節。每筆多一個 `id` 欄位，本專案忽略它。
- **`record_count` 在有 `limit` 時是「本頁筆數」，不是總命中數。** 例：「智慧」全部命中 213 筆，`limit=3` 時 `record_count` 是 3。想知道總數只能自己翻頁加總。
- **500 筆上限**：只要「這次要回傳的筆數」超過 500，上游就回 `{"status":"Fail: record count > 500","record_count":4723,"orig":"0","key":"的"}`，沒有 `record`。
  - 搜「的」（命中 4723 筆）：`limit=0`（不限）、`limit=100000`、`limit=501` 都失敗；`limit=500` 成功。
  - 失敗訊息裡的 `record_count` 恰好是真正總命中數，是少數能一次拿到總數的方法，但要自己解析失敗的 `status`。
  - 命中數 ≤ 500 時 `limit=0` 和很大的 `limit` 都正常（「智慧」213 筆，`limit=0` 與 `limit=100000` 都回 213）。
  - 翻頁驗證：「的」以 `limit=500`、`offset=0,500,…,4500` 共 10 頁，筆數 500×9 + 223 = 4723，`id` 無重複，順序穩定。
  - **本專案的 `search_apocrypha` 不像 `search_bible` 那樣自動分頁合併**（`search_bible` 為 `se.php` 做了分頁，到 5000 筆），`limit` 原樣送上游，所以 `limit>500` 會得到 `ErrUpstream`，訊息為 `status "Fail: record count > 500"`。新專案要不要為次經補分頁，是設計決定。
- `offset` 超過總數：回 `success`、`record_count:0`、`record:[]`（`offset=9999`）。`offset` 只剩一筆時回一筆。
- 次經的命中**沒有書卷導論**（實測 4723 筆中 `chap`/`sec` 為 0 的是 0 筆），也沒有 HTML 標籤、沒有 `【1】` 之類的註腳記號；單節最長 435 字。這與使徒教父不同（那邊搜尋會命中數 KB 的 HTML 導論），次經不需要截斷或清理。
- `chap=0` 查 `qsub.php` **不是導論**：`bid=103&chap=0` 實測回的是第 1 章全部 22 節（被當成第 1 章）。

### 2.3 錯誤與怪癖

| 情況 | 上游行為（2026-10-19 實測） | 本專案處理 |
| --- | --- | --- |
| `q` 為空 | `status:"Fail: Empty Query"` | 呼叫前就擋掉：`Invalid parameter 'query': must not be empty`，不打上游 |
| `sec` 格式不合（例 `abc`） | `status` 內夾帶上游 SQL（`Fail:select bible.engs,… from c1933 … submain.chineses='比' … bible.sec=abc …`），洩漏資料表與欄位名稱 | 呼叫前以 regexp `^[0-9]+(-[0-9]+)?(,[0-9]+(-[0-9]+)?)*$` 擋掉 |
| **`bid` 超出範圍（例 116）** | **不報錯，靜默回第 101 卷（瑪加伯上）第 1 章共 63 節，沒有 `prev`** | 本地解析書名，數字也要在 101–115，否則 `Not a book of this collection (101-115)`；不會把 116 送給上游 |
| 章節不存在 | 成功、0 筆 | 回 `verse_count:0`、`book_id:"未知"`、`verses:[]` |
| `limit` 使結果超過 500 | `Fail: record count > 500` | 轉成 `ErrUpstream`，訊息含 status |
| `status != "success"` | 其他失敗字串 | 一律轉成 `ErrUpstream` |
| HTTP ≥ 400 | — | `ErrHTTP`；連線失敗 `ErrNetwork`；JSON 解析失敗 `ErrParse` |

最重要的一條是 `bid=116` 靜默回第 101 卷：**若新專案不先驗證 `bid`，使用者打錯書號會得到「看起來正常」的別卷經文。**

## 3. 轉換與清理（從上游到輸出）

1. **書名 → 編號**：工具收到的 `book` 可以是中文簡稱、全名、英文縮寫、英文名或數字，由本地表解析成 `bid`，上游只收數字（§4）。
2. **簡體書名**：解析失敗時，把簡體字逐字轉成繁體（`foldSimplifiedBook`，用 `s2tBookChars` 字表）再查一次，所以 `友弟德传`、`德训篇` 可用。
3. **搜尋關鍵字一律轉繁體**：`hanzi.ToTraditional(keyword)` 才送出。原因：上游經文是繁體，簡體關鍵字會找不到。
4. **回傳文字不轉簡體**：這 3 個次經工具沒有 `use_simplified` 參數，`bible_text` 原樣輸出（繁體）。上游其實支援 `gb=1`（`qsub.php` 實測回「这书是多比的自述…」，`v_name` 也變「1933年圣公会出版」；`sesub.php` 的 `chineses` 與 `bible_text` 也轉簡體），**新專案若要簡體輸出，直接送 `gb=1` 即可，不必自己轉**。要注意：`gb=1` 時關鍵字 `q` 仍要送繁體（本專案對 `se.php` 另有「關鍵字字形要跟著 `gb`」的處理，次經這邊沒有驗證過 `gb=1` 搭配簡體關鍵字，**未驗證**）。
5. **JSON 數字/字串保留**：`bid`、`chap`、`sec`、`record_count` 用 `json.RawMessage` 讀，再用 `norm()` 重新編碼（去掉 `\uXXXX` 跳脫、保留 number 或 string 的原形、不跳脫 HTML 字元）。
6. **`book` 欄位以本地表為準**：經文結果的 `book` 一律是解析後那本書的中文名（`多俾亞傳`，而非上游的 `比`）；搜尋結果依命中的 `bid` 查表，查不到才用上游 `chineses`，`bid` 為空/0 時 `book` 為空字串。
7. **預設值**：上游沒給版本時，`version` 補 `{code:"c1933", name:"1933年聖公會出版"}`（上游實際一律給）。
8. **不處理的**：沒有正規化異體字（輸出保留 `爲`、`眞`、`着`、`衆` 等上游字形，搜尋時可能因字形不同而漏掉，例如「真實」與「眞實」；上游是否自動視為相同、是否值得用 `hanzi` 折疊後比對，**未驗證**）；沒有拆段落；沒有去標點。
9. **輸出格式**：縮排 2 空格的 JSON 字串，不跳脫 HTML、中文不轉 `\u`。在 MCP 層同時送 text content 與 `structuredContent:{"result":"<同一字串>"}`。

「本專案中文名」承襲 Python 版用的天主教/通行譯名（瑪加伯、多俾亞、德訓篇、智慧篇），而經文本身是 1933 年聖公會譯本，用的是另一套名字（經文裡是「多比」「瑪喀比」）；上游 `chineses` 是更短的簡稱。三者並存，所以同一本書會有多個名字，別名表要都收。

解析規則（`ScriptureSet.resolve`）：
- 純數字：必須在 101–115，否則報錯（43、116 都被拒）。
- 其他：精確比對別名；英文（純 ASCII）不分大小寫，中文要完全相同。
- 找不到：先把簡體字轉繁體再比一次。
- 仍找不到：回 `Invalid parameter 'book': <輸入> - Not a book of this collection (101-115). Use the matching list_*_books tool to see the valid names and ids.`

注意事項：
- **`但補` 刻意不收**：Python 版工具說明把它列為可用簡稱，但但以理書的補篇有三本（三童歌、蘇撒拿傳、彼勒與大龍），歧義就報錯，不猜。
- `巴` 在次經是 109（巴錄書），在使徒教父是 213（巴拿巴），兩個集合各自一張表，不能共用別名表。使徒教父工具收到 `Tob` 會被拒（有測試）。
- 以斯拉上/下、瑪拿西禱詞、三童歌、蘇撒拿傳、彼勒與大龍、以斯帖補篇的中文全名是我們依上游簡稱/縮寫整理，未經官方確認（記在 `app_versions.md` 的待決定）。
- 章數沒有內建表。2026-10-19 從「的」的 4723 筆命中統計出的**最大章號（下限，非官方章數）**：101: 16、102: 15、103: 14、104: 16、105: 51、106: 19、107: 5、108: 16、109: 5、110–114: 1、115: 6。若新專案要做章節預檢或導覽，請自行逐書確認；本專案沒做預檢，直接問上游。
- 各卷命中數分布（「的」）：101: 737、102: 482、103: 198、104: 308、105: 1217、106: 401、107: 174、108: 807、109: 122、110: 50、111: 14、112: 43、113: 46、114: 31、115: 93，合計 4723，可當全文筆數的粗略參考。

### 4.1 D24：為什麼不能沿用 Python 原版的編號

Python 參考實作（`FHL-MCP-Server`）的書卷編號和上游實際編號不一致：它送 `bid=101` 查「多俾亞傳」，上游回的是瑪加伯上，再用自己的表標成多俾亞傳，結果書名與內容不符；搜尋結果書名同樣標錯。原版次經只有 9 本，實際上游有 15 本。本專案改用上游編號（以 `bid` → 回傳 `engs` / `chineses` 實測取得）。新專案請**不要**照抄 Python 的表，也不要只信 README。

## 5. 對外工具介面（若新專案也提供 MCP 工具）

| 工具 | 參數 | 預設 |
| --- | --- | --- |
| `get_apocrypha_verse` | `book` (必填 string)、`chapter` (必填 integer)、`verse` (選填 string) | `verse` 省略或 null = 整章 |
| `search_apocrypha` | `query` (必填)、`limit` (integer)、`offset` (integer) | `limit` 10、`offset` 0 |
| `list_apocrypha_books` | 無 | — |

參數寬鬆規則（沿用 Python 原版行為，D5/D6）：`chapter`、`limit`、`offset` 可傳數字字串（`"1"`）；值為 `null` 視同沒給。

### 5.1 `get_apocrypha_verse` 輸出（欄位順序固定）

```json
{
  "status": "success",
  "query_type": "apocrypha_verse",
  "book": "多俾亞傳",
  "book_id": 103,
  "chapter": 1,
  "verse": "1-3",
  "version": {"code": "c1933", "name": "1933年聖公會出版"},
  "verse_count": 3,
  "verses": [{"book": "多俾亞傳", "book_id": 103, "chapter": 1, "verse": 1, "text": "這書是多比的自述。…"}]
}
```

- `verse` 是請求時的原字串（含範圍寫法，輸出不去空白），沒給時是 `null`；送給上游的 `sec` 則會先去掉前後空白（`" 1 "` → `1`）。
- 找不到內容時：`book_id:"未知"`、`verse_count:0`、`verses:[]`（此時 `book` 仍是解析後的中文名）。
- 每筆 `verse` 的數字型別沿用上游。

### 5.2 `search_apocrypha` 輸出

`status`、`query_type:"apocrypha_search"`、`keyword`（原輸入，未轉繁體）、`total_count`（= 上游 `record_count`，**是本頁筆數，不是總命中數**，即 D20，名稱有誤導性）、`returned_count`、`offset`、`results[]`（`book`、`book_id`、`chapter`、`verse`、`text`）。無結果時 `results:[]`、`total_count:0`。

### 5.3 `list_apocrypha_books` 輸出

`status`、`query_type:"list_apocrypha_books"`、`id_range:"101-115"`、`book_count:15`、`books[]`（`id`、`name_zh`、`name_en`、`abbreviations`）。純靜態資料，不打上游。2026-10-19 透過 `fhl` MCP 實際呼叫確認回 15 卷。

### 5.4 錯誤格式（D2）

工具錯誤回 MCP 結果 `isError:true`，文字前綴 `Error executing tool <工具名>: `，不帶 `structuredContent`。參數驗證訊息為自訂簡短英文（例：`Invalid parameter 'chapter': required parameter is missing`）。

## 6. 快取與請求量

- `qsub.php` 快取 7 天、`sesub.php` 快取 1 天（TTL 為本專案假設，Python 原版只快取經文 7 天、搜尋 1 天）。快取 key 含伺服器、端點與全部參數；只快取 `status == "success"` 的回應，所以 `Fail: record count > 500` 不會被快取。
- 同樣的請求同時進來會合併成一次上游呼叫。
- 這兩支端點沒有發現速率限制（本次 20 次請求，每次間隔 1.5 秒，無異常），但沒有做壓力測試，**未驗證**。
- 整章最多 73 節（耶利米書信）是這次實測看到的；單次回應量小，不需特別分頁。

## 7. 設計建議（給新專案）

1. 分三層：**書卷表 + 解析**（純資料，不依賴任何 SDK）→ **上游 client**（可注入、可 mock）→ **工具/介面層**。本專案的 `ScriptureSet` 讓次經與使徒教父共用同一份引擎，只差端點函式、編號範圍、預設版本與 `query_type` 前綴。
2. **先驗證參數再打上游**：空 `query`、不合法 `verse` 會讓上游回怪訊息（甚至洩漏 SQL），超出範圍的 `bid` 會被靜默換成第 101 卷。這三種都要在本地擋。
3. **搜尋要處理 500 筆上限**：`limit` 不可超過 500，`limit=0` 在命中超過 500 時也會失敗。要支援「全部命中」就得自己以 500 為一頁翻頁；失敗回應裡的 `record_count` 可當總數。
4. **簡繁處理要分開想**：書名簡轉繁（解析用）、關鍵字轉繁（送上游前）、輸出簡體（建議直接用上游 `gb=1`）三件事互相獨立。
5. **書名要有一張自己的對照表**：同一本書有本專案名、上游簡稱、經文內名稱三套，介面顯示用哪一套要先決定。
6. **版權**：1933 年聖公會譯本由信望愛提供。本專案沒有查證其再散布條件；若新專案要快取到本機、整包下載或重新發布，請先向信望愛確認。
7. 不要信 Python 原版的書卷編號（D24），也不要假設上游數字欄位型別固定。
